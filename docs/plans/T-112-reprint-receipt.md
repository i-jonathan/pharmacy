# T-112 Reprint a receipt from sales history

Card: T-112 (split from T-048) · Branch: feat/T-112-reprint-receipt

## Goal

Staff can reprint the receipt of any completed sale from Sales History, for the next release. The
copy is clearly marked as a reprint, shows what happened to the sale since (returns), and the
reprint is logged.

## What I found

- `code` The only receipt code is `printReceipt()` in `frontend/src/next/composables/usePos.js:256`.
  It reads the live cart, so it cannot print a past sale.
- `code` POS slips carry a number made up in the browser (`"POS-" + time`, `usePos.js:258`). The
  real number is generated by the server (`service/sales.go:52`, `model/sales.go:70`) and is what
  Sales History shows and searches. `POST /sales/` answers only `{"msg": "Saved Successfully"}`
  (`controller/sales.go:54`), so the POS never learns it. A customer's slip matches nothing in
  history today.
- `code` `/sales/filter` already returns everything a receipt needs: number, cashier, date, items,
  totals, payments, returns (`types.SaleResponse`). The detail panel has `totalPaid`, `change` and
  `returnedRefund` (`SalesHistory.vue`).
- `code` The customer name is typed at the POS but never stored (BOARD T-040), so a reprint cannot
  show it.
- `code` Item names go into the slip's HTML unescaped (`usePos.js:265`).
- `code` A blocked popup makes `window.open` return null, so `w.document` throws after the sale has
  saved. `handleCompleteAndPrint` then shows an error and skips `clearCart` (`PosView.vue:234`).
- `code` `FetchSalesHistory` dereferences `*p.Manufacturer` (`service/sales.go:265`, `:292`), but
  `product.manufacturer` is nullable (migration 3). If the query at `repository/query.go:234` feeds
  it, a sold product with no manufacturer would crash the history request. To confirm with a test
  in step 1; the fix is a nil-safe read.
- `code` `audit_log` needs no migration for a new action; entity type and action are free text.
- `web` Reprints are commonly marked as duplicates (Infor, commercetools, Comarch), and Comarch
  records the person and date of each copy. Some systems gate reprints behind a permission (RMH,
  Astana). No independent source says which control works best.
- `web` Skipped: Nigerian receipt rules. The reprint repeats the stored sale and changes no record.

## Decisions for you

1. **Log every reprint?** Recommended: yes. One audit entry per reprint, no migration. Without it
   the feature is frontend only, but nobody can tell who reprinted what.
2. **Put the real receipt number on POS slips?** Recommended: yes. It touches `CreateSale`, but
   otherwise an original and its reprint show different numbers. Slips already printed keep their
   `POS-` number.
3. **Who can reprint?** Recommended: anyone who can open Sales History, since cashiers handle this
   at the counter and each reprint is logged. A new permission would need a migration.

## Design

**Backend**
- `CreateSale` returns the receipt number; the controller adds `receipt_number` to its reply. On a
  duplicate retry key it looks up and returns the stored sale's number.
- `POST /sales/{id}/reprint`: confirms the sale exists (404 if not), writes the audit entry
  (`sale`, `receipt_reprinted`, details hold the receipt number), and returns `reprinted_at`. Same access as the other `/sales` routes.
- No migration, no new permission.

**Frontend**
- New `lib/receipt.js`: `buildReceiptHtml(receipt)` escapes every value and lays the slip out for
  an 80mm roll (`@page { size: 80mm auto; margin: 0 }`, 72mm wide, one line per item with the
  quantity, price and line total underneath). `printReceiptHtml(html)` prints through a hidden
  frame, so there is no popup to block.
- `usePos.js` prints through it with the number from the server. If printing fails the sale is
  still finished, the cart clears, and the message points to Sales History.
- `SalesHistory.vue`: "Reprint receipt" opens a preview dialog (shown also for fully returned
  sales). Print records the reprint first, then prints the copy stamped with the server's time. If recording fails nothing prints.
- Printer setup (owner's till: 80mm USB thermal printer, Edge): the printer's paper size in
  Windows must be the 80mm roll. `msedge --kiosk-printing` (from model knowledge, to be checked on
  the till) prints without the dialog. Direct ESC/POS over USB is left to T-048.

## Steps

1. `CreateSale` returns the receipt number, including on a duplicate key. Test: extend
   `idempotency_test.go`.
2. Reprint service method, controller, route. Tests: audit entry written, unknown sale gives 404.
3. `lib/receipt.js`, and move the POS onto it.
4. Reprint button and preview in Sales History.
5. `make assets`, then check in the running app.

Built as planned, plus: `manufacturerName` (nil-safe) fixed a real crash, confirmed by the
integration test: a product with no manufacturer broke Sales History.

paper to the 80mm roll, and optionally start Edge with `--kiosk-printing`.
